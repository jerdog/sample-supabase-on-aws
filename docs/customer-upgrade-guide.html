1. Upgrade Overview

Phase 2 adds a new Storage subsystem on top of the existing platform, and enhances Edge Functions, project lifecycle management, and security. Key changes:

CapabilityDescription
Storage (new)Object storage service with multi-tenant isolation. Adds one S3 bucket + one storage service + a database storage schema.
Edge Functions verify_jwtSupports disabling JWT verification at deploy time (for webhook scenarios), configurable in a single deploy step.
Project pause / resume / deleteAfter pausing, the data plane truly stops serving requests; resuming restores it.
Secrets override semanticsA secret with the same name overrides rather than stacks.
Function error classificationCode errors return 422 (instead of a misleading 404).
Security hardeningTenant isolation, secret lifecycle, and dependency CVE fixes.
Zero impact on existing data:The upgrade does not modify any end-user tables or data; all database changes are additive (new tables / new schemas) and do not affect existing reads/writes. Existing API keys and Edge Functions remain valid.

2. Prerequisites

The operations machine performing the upgrade must have:

  • docker (able to build linux/amd64 images)
  • node, pnpm, go, deno (build toolchains for the various services)
  • aws cli (configured with credentials for the target account)
  • AWS CDK (the target account has already completed cdk bootstrap)
  • jq (required by the test scripts)
Config files are not part of the code:config.json and certs/ are not under version control (they contain sensitive deployment values). The upgrade process will not overwrite them, but please confirm their contents are valid for the current environment.

3. Pre-Upgrade Preparation

1

Back Up Configuration

cp config.json config.json.bak
2

Confirm config.json Contains the storage Section

Phase 2 introduces Storage, so config.json needs to include a storage section (the baseline version does not have one). If it is missing, add it by referring to the config template config.production.json:

"storage": {
  "bucket": { "mode": "create" },   // create = create a new bucket; or "existing"+"name" = reference an existing bucket
  "fileSizeLimitBytes": 52428800,      // per-file limit (50 MiB)
  "imageTransformationEnabled": false
}

Verify: cat config.json | jq '.storage'

3

(Recommended) Eliminate the Gateway Single-Point Interruption Window

If the gateway service kong has a desiredCount of 1, restarting it during the upgrade will cause a brief interruption (tens of seconds) to the data plane. It's recommended to set kong.desiredCount to 2 in config.json and deploy it separately before the upgrade (during a low-traffic window); after that, gateway upgrades can be zero-downtime.

4. Pull the Latest Code

First decide which path to take:

  • The operations machine already has a git repository for this project and a clean working tree → use Method A (git pull).
  • The operations machine has no repository, or the working tree has unconfirmed local changes → use Method B (git clone).
  • If you prefer to copy the new version's code into a new project directory and reuse the original config to update the existing environment → use Method C.

Commands to check: git rev-parse --is-inside-work-tree and git status --short.

All three methods produce the same deployment result:As long as the stack name, account/region, and physical resource names stay unchanged, A / B / C are all in-place updates of the same environment, and the subsequent build/deploy steps are identical. The only difference is "how the new code gets onto the operations machine."

Method A: git pull (incremental update)

Complete the following pre-cleanup steps before running pull.Otherwise, the pull may fail due to local file conflicts.
# Pre-step 1: remove the local untracked lockfile
#   In earlier versions this file was not under version control, so the ops machine may have a local copy;
#   the new version has added it to git — if not cleaned up, pull will report
#   "untracked working tree files would be overwritten by merge".
rm -f app/function-deploy/pnpm-lock.yaml

# Pre-step 2: check for local changes (if status is non-empty, stash first)
git status
git stash        # only if there are local changes you need to keep

# After pre-steps are done, pull the latest code
git fetch origin
git pull origin main

# If you ran stash earlier and still need those changes: git stash pop

Method B: git clone (fresh checkout)

# 1) Fresh clone into a new directory
git clone <repository-url> supabase-app
cd supabase-app
git checkout main

# 2) Migrate local files that aren't tracked by git (copy from the old ops directory)
cp <old-dir>/config.json ./config.json
cp -r <old-dir>/certs ./certs

# 3) Confirm config.json contains the storage section (see Section 3, Step 2)
cat config.json | jq '.storage'

Method C: Copy into a new project directory, reuse the original config to update the existing environment

If you prefer to copy the new version's code into a new project directory (rather than pulling in the original directory), then copy in the existing environment's config and redeploy, this will update the existing environment in place (it will not create a second one). This is fundamentally the same as Method B — the only difference is it's used to "update an existing environment" rather than "stand up an independent environment."

# 1) Prepare the new version's code directory (clone or extract the new version)
git clone <repository-url> supabase-app-new
cd supabase-app-new && git checkout main

# 2) Copy config and certs in from the original environment (key point: reusing the original config = updating the original environment)
cp <old-dir>/config.json ./config.json
cp -r <old-dir>/certs ./certs
cat config.json | jq '.storage'    # confirm it contains the storage section
To update the existing environment, the following three items must exactly match the original environment (reusing the original config satisfies this):
  • Deployment stack name SupabaseStack (hard-coded in the code, don't change it) — the deploy tooling identifies its target by stack name; only a matching stack name will update the existing stack instead of creating a new one.
  • The same AWS account and region (config.json's project.accountId / project.region).
  • The physical names of each resource are unchanged: infraStack.cluster.name, loadBalancer.name, studioLoadBalancer.name, workerRds.clusterIdentifier, secrets.prefix, domain.baseDomain.
If all three match → the subsequent cdk deploy SupabaseStack performs an incremental update (in-place upgrade) of the existing environment, and will not produce a second set of resources.
Reminder — the reverse also applies:If any one of the three items above is changed (especially the stack name or account/region), the behavior changes — this can create a brand-new parallel environment, or cause the deployment to fail due to physical resource name conflicts. To update the existing environment, do not change them.

5. Build and Push Images

Build the service images involved in this upgrade and push them to ECR (the script automatically creates any missing ECR repositories):

./build-and-push.sh storage          # new service
./build-and-push.sh tenant-manager
./build-and-push.sh functions
./build-and-push.sh function-deploy
./build-and-push.sh kong             # Required: the gateway route config includes Storage routes
./build-and-push.sh auth
You must rebuild kong:The gateway's route configuration (kong.yml.tpl) added Storage routes in Phase 2. If you keep the old gateway image, Storage data-plane requests will return 404 no Route matched.
Confirm which services need rebuilding:Run git diff <baseline-version> HEAD --name-only | grep '^app/' — any service with code changes under app/ needs to be rebuilt. This time that's storage, tenant-manager, functions, function-deploy, kong, and auth.
Build tip:If the auth service (Go) times out fetching dependencies during the build, its Dockerfile is already configured with a mainland China dependency mirror/proxy; function-deploy's lockfile is already under version control, so a clean checkout is enough to build.

6. Deploy (CDK)

1

Compile and Review Changes

cd infra && npm run build
cdk diff SupabaseStack

Expected changes: a new S3 bucket, a new storage service, and updates to several task definitions (TaskDefinitions). Confirm the changes do not include a "replace" of any stateful resource such as the database cluster, S3 bucket, or cache — a normal upgrade only updates task definitions and should never replace stateful resources.

Version compatibility:Make sure the CDK CLI version is compatible with the project's aws-cdk-lib dependency version. If you see Cloud assembly schema version mismatch, upgrade the CDK CLI or pin aws-cdk-lib to a matching version.
2

Run the Deployment

cdk deploy SupabaseStack --require-approval never

This step creates the new S3 bucket and storage service, and updates the task definitions. Watch each service's rollout status during deployment.

No automatic rollback:The deployment does not have the circuit breaker enabled, so a bad image will not automatically roll back. Monitor the deployment status until it reaches COMPLETED: 
aws ecs describe-services --cluster <cluster-name> \
  --services storage-api kong-gateway tenant-manager \
  --region <region> \
  --query 'services[*].[serviceName,deployments[0].rolloutState]'

7. Refresh Service Images (Critical Step)

Mandatory — do not skip:CDK references images via the :latest tag. cdk deploy only triggers a service to pull a new image when the task definition's structure changes. For services whose code was updated but whose task definition did not change, cdk deploy will not make them pull the new image — the service will keep running the old code.

Therefore, after the deployment completes, you need to force a refresh of every service whose image was rebuilt:

for svc in kong-gateway tenant-manager functions-service \
           function-deploy auth-service storage-api; do
  aws ecs update-service --cluster <cluster-name> \
    --service "$svc" --force-new-deployment --region <region> \
    --query 'service.deployments[0].rolloutState' --output text
done
A note on service names:ECS service names and ECR repository names may differ (e.g., repositories functions-service / kong-configured correspond to services functions-service / kong-gateway). You can use aws ecs list-services --cluster <cluster-name> to look up the actual service names.
Database migrations (automatic):Schema changes to the platform database and each tenant database run automatically when the corresponding service starts. They are all additive operations, requiring no manual intervention and no rollback.

11. Upgrade Mechanism Quick Reference (Path A/B · Service Name Mapping)

How to make a change take effect during an upgrade depends on what you changed. Picking the wrong path is the most common reason for "I changed it but nothing happened."

Path A: Service Code Changes (Docker Images)

Changing any service under app/* (Kong config, GoTrue, tenant-manager, Studio, etc.) requires rebuilding the image and forcing ECS to pull it. cdk deploy will not pull a new image if the image tag is unchanged — the task definition still points at :latest, so ECS keeps the old task running. You must force a refresh:

# 1. Rebuild and push (pushes both :latest and :<git-sha>)
./build-and-push.sh <service>      # e.g. kong, auth, tenant-manager
# 2. Force ECS to pull the new :latest and replace the running task
aws ecs update-service --cluster <cluster> --service <service-name> --force-new-deployment --region <region>
# 3. Wait for the rollout to stabilize
aws ecs wait services-stable --cluster <cluster> --services <service-name> --region <region>

The ECR repository name and ECS service name differ for some services:

build-and-push.sh argumentECS service name
kongkong-gateway
authauth-service
functionsfunctions-service
storagestorage-api
tenant-manager / studio / function-deploy / postgres-metaSame name

Path B: Infrastructure Changes (CDK)

Changes to infra/ (VPC, RDS, ECS task definitions, ALB, IAM, env, etc.) go through CDK. Task definition changes (new env vars, CPU/memory, etc.) will automatically roll the service:

cd infra && npm run build && npx cdk diff SupabaseStack   # preview
npx cdk deploy SupabaseStack --require-approval never
Rule of thumb:Image content changed → Path A (force-new-deployment); task/infrastructure definitions changed → Path B (cdk deploy). If both changed (e.g., a new image plus a new env var it needs to read), do B first, then A.

Kong Notes (DB-backed Declarative Configuration)

Kong runs in DB-backed mode, importing kong.yml.tpl via kong config db_import on startup — this is an incremental upsert that never deletes entities removed from the config. The entrypoint script runs an idempotent self-heal (heal-stale-plugins.lua) on every startup, clearing out service-level auth plugins left over from old configs. So for kong-gateway, simply rebuild + force-new-deployment — no manual DB cleanup is needed.

Auth Schema Notes (Template Cloning + Existing Tenants)

New tenant databases are cloned from the cached supabase_template database, rather than having DDL run against an empty database; and the schema DDL uses CREATE TABLE IF NOT EXISTS, which is a no-op against tables that already exist. So changing only the CREATE TABLE statements in auth-schema.ts can never backfill new columns — neither the template nor existing tenant databases would get the new columns, and newly created tenants would keep cloning the stale template.

On startup, tenant-manager runs a set of idempotent ALTER TABLE ... ADD COLUMN IF NOT EXISTS statements (see AUTH_SCHEMA_HEAL_STATEMENTS) against the template database and every existing tenant database on every registered instance, so both fresh deployments and upgrade deployments converge on the current schema. This self-heal is idempotent (columns that already exist are skipped) and fail-open (locked/paused tenant databases are automatically skipped, and it will never block startup). It only adds columns/constraints — it never deletes or modifies any existing data. So for tenant-manager, simply rebuild + force-new-deployment — there's no need to manually drop the template database or backfill columns database-by-database.

Table changes must ship with a matching patch:After adding a column to a table in auth-schema.ts, you must also add a corresponding ADD COLUMN IF NOT EXISTS statement to AUTH_SCHEMA_HEAL_STATEMENTS — otherwise the change stops at the code and never reaches the database.

11.1 Storage Object Storage (New)

Deployment: Adds an S3 bucket + storage service + database storage schema. config.json's storage.bucket.mode determines where the bucket comes from: create = CDK creates and manages a new bucket; existing+name = reference an existing bucket (CDK only grants permissions, it does not create/delete it). Requires rebuilding storage and kong (the gateway includes the Storage route).

# config.json
"storage": { "bucket": { "mode": "create" }, "fileSizeLimitBytes": 52428800, "imageTransformationEnabled": false }
# Build + refresh
./build-and-push.sh storage && ./build-and-push.sh kong
aws ecs update-service --cluster <cluster> --service storage-api --force-new-deployment --region <region>

Usage: All Storage requests go through the Kong gateway via the project subdomain (Kong validates the opaque apikey with key-auth, injects X-Project-ID, and mints a short-lived 5-minute JWT for storage-api; storage-api uses it to enforce multi-tenant isolation). Base URL: https://<ref>.<domain>/storage/v1, with every request carrying an apikey: <key> header (anon or service_role opaque key).

Full API quick reference (the newly added object storage data plane; all paths verified against the source at app/storage/src/http/routes/, prefixed with /storage/v1. The fastify wildcard segment * is the object path):

11.2 Function verify_jwt Parameter (webhook scenarios)

Deployment: Rebuild function-deploy (the deploy pipeline persists verify_jwt) and functions (the runtime enforces the actual verify_jwt value). No new infrastructure.

Usage: Include verify_jwt in the metadata at deploy time (no separate PATCH needed). With verify_jwt:false, the function allows anonymous access without a JWT (for webhook callbacks such as Stripe / GitHub).

# Deploy a webhook function (no JWT verification)
# The metadata field in the multipart deploy request (field name verified against deploy.ts):
{ "verify_jwt": false, "entrypoint_path": "index.ts" }

Testing: PROJECT_REF=<ref> ./RUN_TESTS.sh verify-jwt — V1 internal lookup defaults to true, V2 deploy persists it, V3 true rejects anonymous, V4 false allows anonymous (webhook), V5 still works with an apikey, V6 switching back re-enforces it — 6 checks in total (including 1 environment-related skip).

11.3 Project Pause / Resume / Delete

Deployment: Rebuild tenant-manager. Semantics: this is triggered manually by calling the server-side API. After pausing, the data plane truly stops serving requests (the platform database's status leaves active, and the Kong gateway gate blocks access); resuming restores it. This is not automatic.

Usage (admin API, requires an admin key):

curl -X POST "https://<studio-alb>/admin/v1/projects/<ref>/pause"   -H "Authorization: Bearer <admin-key>"
curl -X POST "https://<studio-alb>/admin/v1/projects/<ref>/resume"  -H "Authorization: Bearer <admin-key>"   # /restore is an equivalent alias
curl -X DELETE "https://<studio-alb>/admin/v1/projects/<ref>"       -H "Authorization: Bearer <admin-key>"

Testing: ./RUN_TESTS.sh lifecycle — K0 create project, K1 pause → PAUSED, K2 /resume restores → ACTIVE_HEALTHY, K3 /resume == /restore alias, K4 REST/JS SDK reachable after resume, K5 delete tears down, K6 recreate with the same ref (201 or 409 guard) — 7 checks in total.

How the paused data plane actually stops:It relies on the Kong cache TTL (300s by default) naturally expiring. After pausing, a cached project will be blocked within at most one TTL; new projects take effect immediately.

11.5 Login Enhancements (Google OAuth / Email Password Reset / Admin Password Change)

No new env vars/secrets: Google credentials are entered per-tenant at runtime, and the client_secret is encrypted into the database using the existing ENCRYPTION_KEY.

for svc in tenant-manager auth function-deploy; do ./build-and-push.sh $svc; done
./build-and-push.sh kong
for svc in tenant-manager auth-service kong-gateway function-deploy; do
  aws ecs update-service --cluster <cluster> --service $svc --force-new-deployment --region <region>
done

11.6 Function Deployment Error Classification (404 → 422)

Deployment: Rebuild function-deploy. What was fixed: when a deployment fails due to a syntax error in the function's code, the old version incorrectly returned 404 Function not found (making users think it was a platform bug); the new version distinguishes error types — a code error returns 422 FUNCTION_VALIDATION_FAILED, and 404 FUNCTION_NOT_FOUND is only returned when the function truly does not exist.

Usage: Deploy/invoke normally; the error response body carries an explicit error code, making it easy for customers to self-diagnose.
